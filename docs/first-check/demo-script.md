# 第一次检查演示脚本

> 历史资料：适用于 2026-10-21 初版。当前文档见 [课程检查材料目录](../submission/README.adoc)。

建议提前下载依赖，完成 `mvn clean verify`。检查当天不要临时更换数据库或部署方式。按 [启动文档](local-run.md) 启动 demo，再执行数据脚本；准备两张浏览器标签页，分别登录管理员和 demo_alice。Token 只存在各标签页内存中，所以两页不会互相覆盖登录身份；演示过程中不要刷新整个网页。

## 一、先解释需求（约 1 分钟）

“我们要统一管理用户能使用哪些业务功能。权限直接分给个人容易遗漏回收，只隐藏按钮又会被直接请求接口绕过。第一次检查采用 RBAC0，把权限组成角色，用户通过角色获得权限并集，并在后端每次请求时校验。”

接着展示 [数据库关系图](design.md)：用户与角色、角色与权限都是多对多，用两张关联表连接；业务系统包含权限；登录会话单独记录。说明本阶段没有继承和互斥，不讲成 RBAC1/RBAC2。

## 二、展示管理员配置（约 3 分钟）

| 步骤 | 实际操作 | 预期效果 | 讲解重点 |
|---|---|---|---|
| 1 | 管理员登录，打开“业务系统” | 显示 demo_finance | 系统只是权限所属分类，未接入真实财务服务 |
| 2 | 打开“权限管理” | expense:list 和 demo:detail | 编码全局唯一；demo:detail 只有权限记录，没有明细接口 |
| 3 | 打开“角色管理”，查看两个角色的“配置权限” | 两者都有 expense:list；复核员还有 demo:detail | 一个权限可以被多个角色持有 |
| 4 | 打开“用户管理”，查看 demo_alice 的“角色与权限” | 两个角色勾选；有效权限两项 | 并集合并去重，不是简单把两份列表拼接 |
| 5（可选） | 新建一个临时用户，设置密码，编辑名称/启停 | 列表刷新；新建时还不能登录，设置密码后才可登录 | 功能拆分清楚；密码仅存摘要 |
| 6（可选） | 新建用户时留空，再输入一个已存在用户名 | 必填提示或中文重复提示 | 前后端都验证，错误不伪装成成功 |

管理员只负责配置权限。管理员身份不自动包含 expense:list，也不能通过 HTTP 创建第二个管理员。演示数据脚本是通过同样的管理员 API 配置，不是绕过鉴权写库。

## 三、证明授权、回收、并集和注销（约 4 分钟）

| 步骤 | 标签页与操作 | 预期效果 | 讲解重点 |
|---|---|---|---|
| 1 | 普通用户页用 demo_alice 登录，打开“我的有效权限” | 两项权限；没有管理导航 | 导航只是可用性设计，后端仍独立拒绝管理 API |
| 2 | 普通用户页打开“报销权限演示”，点击“请求报销列表” | 200；两条固定报销示例 | 数据明确是演示；后端实际校验 expense:list |
| 3 | 管理员页取消 demo_alice 的“报销查看员” | 剩一个角色，有效权限仍两项 | 另一角色仍提供相同权限 |
| 4 | 普通用户页再次点击请求，不重新登录 | 仍为 200 | 共享权限不能被错误回收 |
| 5 | 管理员页再取消“报销复核员” | 有效权限为空 | 最后一个权限来源已去除 |
| 6 | 普通用户页再次请求，不重新登录 | 403；仍保留普通用户身份 | JWT 没有变，后端查的是当前授权 |
| 7 | 普通用户页点击“注销并用旧 JWT 验证 401” | 回到登录页，提示旧 JWT 请求已收到 401 | 401 与 403 含义不同，注销删除服务端会话 |

演示后运行 `python scripts/demo-data.py` 恢复基线，两个用户需要重新登录。也可以由管理员重新勾选角色；同一个仍有效的会话会恢复业务访问。

## 四、展示后端边界与报告（约 2 分钟）

打开 [HTTP 验证结果](evidence/http-verification.json)，指出普通用户请求用户列表、修改别人密码、自行分配角色、创建管理员都被拒绝。报告中的 14 项来源于实际本机 HTTP，不是手写“预期结果”。需要现场复跑时执行 `python scripts/demo-data.py --verify`，它会恢复演示基线并撤销普通用户旧会话。

打开 `evidence/jacoco/index.html` 或构建后的 `target/site/jacoco/index.html`，展开 service、config 和 controller 查看覆盖行。说明 20 项 JUnit、覆盖率与未覆盖风险，不能把覆盖率当成绝对正确证明。

如演示“账号被停用导致失效”：让普通用户保持登录，管理员编辑并停用该用户，然后普通用户点击“刷新”或请求报销，应回到登录页。重新启用后需要重新登录，原 JWT 不复活。

## 五、个人陈述准备提示

每个人应根据自己实际参与的部分，按“需求/问题 → 设计方法与理由 → 代码或页面效果”来讲。可以引用本材料中的模型和流程，但不要声称完成自己没有参与的工作。本材料不生成成员分工，也不替任何人认领贡献。

自由讨论可准备以下解释：

- 为什么多个角色取并集：RBAC0 只有允许关系，不定义拒绝优先或互斥。
- 为什么 JWT 还要数据库会话：单纯验签无法立即使已签发 Token 因注销而失效。
- 为什么不把登录响应里的权限当准则：角色回收之后，旧快照已经过时。
- 为什么管理员标记不放进可配置角色：防止业务授权操作同时变成管理提权入口，课程范围内边界更直接。
- 为什么使用原生网页：复用现有 Spring Boot 与 API，同源部署、零前端构建，团队维护成本低。
- 哪些结论不能保证：本次仅本地 H2；没有真实 MySQL、多实例、部署和大规模负载证据；报销不是完整业务系统。
